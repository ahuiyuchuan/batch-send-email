# 账号冷却池与默认900秒验收

作者：ahui

日期：2026-11-09

## 问题和当前行为

用户指出：一个账号已经发送后取消，再次发送应继续该账号尚未结束的冷却，并要求默认间隔 900 秒。上一版本的 AccountRoundTiming 由每个 worker 新建，ready_at 仅存任务内，因此终态后重建任务确实丢失期限；原默认值为 300 秒。

本轮默认值改为 900 秒（15 分钟），显式 1—3600 整数秒仍兼容。账号完成一批后保留自己的冷却，取消、结束、新建任务均不清零；50 秒后重发继续等待约 850 秒，取消等待不重算或延长。正常退出重启后也从本机 SQLite 恢复剩余时间。降低新任务间隔不能缩短已生效期限，调整后的值仅用于后续登记/尝试。

每轮各有任务账号最多一批；按预检冻结账号优先顺序选择已就绪账号，先跳过冷却者，本轮没有可发账号时才等待最近到期身份。这样 A 已发后取消，B 未登记过可先发，不受 A 冷却阻挡；整轮尝试完成才进入下一轮，避免同一账号抢跑。与上一轮首统一等全部账号的实现相比，这是独立冷却池下的调度修正；每账号分配、内部名单、随机均分及批数均不改变，不重新随机或转移收件人。

| 场景 | 行为 |
| --- | --- |
| A 已完成一批、间隔900，50秒后重发 | A 等剩余约850秒，不立即发送，也不重算满900秒。 |
| 冷却等待中取消，再次发起任务 | 继续同一固定期限，正常取消不更新期限。 |
| B 从未登记尝试、A仍冷却 | 本轮 B 可先发；本轮所有待发账号都冷却时才等待最近期限。 |
| 改名、重排、改授权码或删除重加相同发件邮箱 | 规范化身份相同，原冷却仍生效。 |
| 新任务改成更短间隔 | 不能缩短已经保存的原期限，后续尝试才使用新值。 |
| SMTP 失败/结果不明 | 该账号同样冷却；待核实收件人仍禁止自动重投，不因换任务或账号绕过。 |
| 任务结束、无下一批 | 不创建无用倒计时，账号自身剩余期限保留供后续任务。 |

## 持久化、失败和兼容

SQLite 保持 schema 4，不新增表；现有 settings 键 `smtp_sender_cooldowns_v1` 保存 version=1 的小型目录，每条含规范化公开 From 邮箱、UTC 记录/截止毫秒和可空 pendingIntervalSeconds。旧库缺少键表示首次使用，读不写空标记。旧版没有分账号冷却记录，不能根据共享收件历史猜测回填，升级前的尝试不追溯创建期限；新池从本版本登记的投递开始保留。冷却身份去首尾空白、合并 ASCII 大小写，刻意保守合并发件邮箱大小写；不推断别名、认证账号或邮箱服务商关系，也不改变收件历史的地址规则。所有账号的成功历史、待核实及排除继续共用。

运行期共享池在 AppState 中保存单调期限，首次发送前从 SQLite 恢复一次；随后系统时间校准不重算运行期已有期限。正常重启按 UTC 剩余时间恢复，系统时钟回拨时保守保留较晚截止。目录 revision、模板、QQ 登录和账号凭据格式不受影响。

网络尝试前必须先持久登记 pending 与期限，失败则不连接 SMTP。结果处理完成后先保留内存期限，再持久清 pending、合并完成时刻加本次间隔；数据库事务只允许取 max，写失败停止后续任务，不能按“失败后继续”绕过存储故障。若 SMTP 已接受且成功记录已提交，仅冷却刷新失败，保留正确成功人数与历史，不改成待核实或假称未投递。

pending 表示程序可能在交互中崩溃，或完成后的冷却尚未落盘。下次首次恢复会保守补足一次原间隔、持久固定截止并清 pending，后续正常重启只恢复剩余，不不断续期；恢复写失败整体回滚并禁止投递。普通取消等待没有 pending，也不触发这项延长。只预检、取消确认和尚未轮到登记的账号不触发冷却；如果实际投递准备已登记，但之后本地收件预留失败零 SMTP，则保守保留该账号一次登记期限，不从失败时刻续期。这是避免跨模块回滚误删旧期限的明确异常取舍。

持久记录严格校验版本、身份、时间、重复项及大小，损坏或不可读时明确报错，不当成空池。成功写入时只清理确认过期且无 pending 的记录；未到期或 pending 不能被容量限制淘汰。上限10000条、4MiB，达到上限拒绝新增而不清空旧等待。

新增持久键只向后兼容读取，旧版本程序不知道该键，回退后无法遵守跨任务冷却；如需回退，先正常退出并保留完整应用数据备份，等待未结束的冷却，不降低 user_version 或删除键来绕过。应用数据目录仍为 `%LOCALAPPDATA%/com.ahui.qq-group-exporter`，更换 EXE 路径不清数据。
