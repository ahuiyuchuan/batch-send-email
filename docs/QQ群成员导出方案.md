# batch-send-email：群成员整理与邮件投递实现方案

作者：ahui

更新日期：2026-11-17；最初编写日期：2026-11-10

版本：1.0.0。本文对应当前代码；真实 QQ 账号、目标群和真实 SMTP 投递尚未联调，不把模拟测试当作平台可用性证明。文末保留各轮增量设计及当时的回滚包名；当前公开发布方式以下文及 README 为准。

## 1. 目标与交付形式

面向 Windows 10/11 x64：使用自己已经加入群的普通成员账号读取数字 QQ 号，核验名单，排除其他群的重合成员、当前获取账号的好友及本机已发送记录，预览后导出，或追加到写信页进行 SMTP 投递。群主或管理员不是设计前提，但实际可读范围仍由 QQ 接口、账号和群状态决定。

公开交付为单个便携 `Batch-Send-Email-v1.0.0-Windows-x64.exe`，源码原始产物为 `target/release/batch-send-email.exe`，构建脚本复制为指定输出目录下的 `batch-send-email.exe`。公开名称采用 `batch-send-email`，应用标识继续使用 `com.ahui.qq-group-exporter`，避免升级改名后失去原数据库、模板、共享历史和凭据。它通过系统 WebView2 显示界面，不另开浏览器，也不启动本地 HTTP 服务。使用者不需要安装 Node.js、Rust 或 C# 环境；缺少 WebView2 Runtime 时仍需安装微软运行时。“单 EXE”指分发文件，运行后会产生本机 SQLite、WebView2 缓存及正常临时文件。

不提供权限提升、自动加好友或聊天记录。QQ 成员读取单账号，SMTP 支持多个发件账号；邮件队列仍串行执行。读取失败会显示原因，不把无权限或接口异常解释为空群。

## 2. 技术选择与模块边界

采用 Tauri 2 + Rust + React。WebView2 是 Windows 上承载界面的运行时，并不要求使用 C#；业务命令由 Rust 校验后执行。

| 部分 | 当前选择 | 职责 |
| --- | --- | --- |
| 桌面宿主 | Tauri 2、Rust | 原生窗口、受控 IPC、保存与附件对话框、关闭清理。 |
| 界面 | React 19、TypeScript、Vite、Lucide 图标、Sonner 2.0.8 | 连接账号、群选择、过滤、表格、写信、历史管理、操作浮层与深浅外观。 |
| 网络与任务 | reqwest、Tokio | QQ 扫码与成员读取、超时、取消、身份核对。 |
| 本机数据 | rusqlite、SQLite | 最近名单及过滤快照、全局已发送记录、公开 SMTP 设置。 |
| 文件导出 | rust_xlsxwriter、csv | Excel、CSV、TXT 的文本类型、编码、转义和安全写入。 |
| 邮件 | lettre、ammonia | TLS SMTP、密送分批、基础 HTML 清理和发送结果记录。 |
| Windows 界面引擎 | 系统 WebView2 Runtime | 渲染打包的静态资源；业务网络请求由 Rust 执行。 |

```text
WebView2 中的 React 界面
          │ Tauri IPC
          ▼
Rust 宿主 ── QQ 网页接口 / SMTP
          │
          ├─ 号码校验 → 去重 → 人数核验 → 群排除 → 好友排除 → 已发送过滤 → 手动排除叠加

```

`frontend/` 管交互，`src-tauri/` 管桌面命令与任务生命周期，`crates/member-core/` 管 QQ 网页读取、核验、过滤、导出、数据库与邮件。页面不解析 QQ 私有响应，不保存 Cookie，也不能传任意本机路径让后台读取。

## 3. 网页扫码与成员读取

成员读取统一使用程序内网页扫码会话和 `qun_info/get_members_info_v1` 流程。本项目没有真实账号验证，不能保证任意群成功；旧群管理接口不能直接作为普通成员能力的证明。

扫码成功后先核对真实数字 QQ 号，再读取该账号已加入群并保存目录；提交时以本次授权账号直接替换当前账号，不要求账号相同。只有核验及群目录保存均成功才切换，取消/失败保留旧连接。提交前检查 pending_web Arc 指针，数据库写入后再次检查，迟到扫码不能覆盖已取消或较新的扫码。前端同样用扫码代次和状态事件代次丢弃旧响应。切换后清空选群、当前成员快照及任务，不合并不同账号的获取上下文；独立邮件草稿和明确冻结的原收件版本保留。

数字 QQ 号从网页 `uin` 取得，不把内部 `uid`、`openid`、昵称当作 QQ 号。缺失角色保持未知，不推断为普通成员。网页跳转限于可信 QQ 登录域；Cookie 仅在 Rust 当前进程的 CookieStore 中管理，并继续遵守远端域名、路径及过期规则，不进入页面、浏览器存储、SQLite、文件或日志。删除旧持久会话模块、七天本机有效期及启动恢复；新进程始终 signed_out，关闭程序后需重新扫码。启动仅删除应用数据目录中固定旧文件 qq-session.bin，不读取/解密、不递归；失败记录无路径安全日志并继续启动，下一次重试，始终不采用旧凭据。SMTP 密文与数据库不受影响。明确认证错误撤下当前账号/目录/名单并提示扫码；网络、权限及业务失败不冒充登录失效。

## 4. 用户操作与过滤规则

1. **连接。** 在程序内扫码，区分等待扫码、等待手机确认、成功、过期与失败；过期后刷新。顶部显示账号昵称和默认脱敏的当前账号 QQ 号，可主动查看全号。
2. **选群。** 左侧按群名或群号搜索，单选目标群 A；右侧可多选排除群 B、C，并按需勾选“排除我的 QQ 好友”（默认关闭）与“过滤已发送”。所有群必须来自当前账号和来源，目标群不能排除自身。
3. **获取。** 先逐一读取全部目标群并核验、合并去重，再逐一读取排除群。获取期间锁定连接、群选择、历史变更和发送等冲突操作，显示真实步骤并可取消。任一群读取失败或取消时保留上次完成结果，不发布半套过滤结果，迟到响应不能覆盖新任务。
4. **核对。** 显示目标原始有效人数、群排除人数、好友实际排除人数、已发送过滤人数和最终人数；“筛选后成员”与“已过滤”分开查看，后者保留原因及相关排除群。
5. **导出或写信。** 导出使用完整固定结果，不受搜索影响。成员行支持点击、空格或 Enter 选择，并与复选框共用禁选判断；拖选文字和行内按钮不误触勾选。还可通过本页全选、选择搜索匹配项和跨页勾选确定部分成员；已过滤成员只读核对，不能加入收件名单。

群列表与内容区分别滚动，主导航保持可用。群快照按账号、来源和群隔离，切群读取该账号该群独立保存的最新结果，没有时显示空态；每群最新不受最近 20 份历史记录淘汰影响；获取返回的总人数更新侧栏，不用已过滤数量填充未知总数。时间统一显示完整年月日时分秒。get_group_snapshot(groupId或groupIds) 只读取当前账号已加入群对应单群／组合的本机快照，不联网；export_members(format, snapshotId) 按明确版本导出，不再使用全局最近结果，指定版本在每群最新与最近历史两处均不再保留时要求重新获取，旧前端须与新 EXE 一起更新。成员选择与写信组成一条连续流程。写信页持续展示群名、群号、名单时间、筛选后名单与本封已选人数；排除群和筛选过程收在可展开详情中，待核验或版本更新限制仍保持可见。可查看群收件人明细并返回来源群和原名单版本调整。更换已绑定的收件范围需确认，取消保持原范围，确认后只替换群收件人，保留主题、正文、附件与补充邮箱。重新获取或更换账号不会悄悄改写编辑中的收件范围。

规则固定为：`目标群按 QQ 号去重 −（排除群 B ∪ 排除群 C …）− 获取账号的好友 − 已发送 QQ 号 − 全局手动排除`。好友与已发送过滤均可关闭。原始快照保持群排除、好友排除、已发送过滤顺序，之后叠加实时手动排除，同一人只按首次原因计数。

例如 A 有 1000 个有效号码，B/C 与 A 的去重交集为 30 个，剩余名单有 20 个好友，再有 10 个命中已发送历史，全部选项启用时最终为 940 人。B/C 自身人数不是直接扣减量；同昵称不同号码不相互排除。

已发送历史是本机全局的，不按群或提取账号分隔。数字 QQ 邮箱归一化后可参与号码过滤；普通其他域邮箱不猜测 QQ 号。导出不等于发送，手工标记表示用户自行确认，不能证明程序曾投递。

### 好友关系与名单版本

仅勾选“排除我的 QQ 好友”时，使用当前任务的同一 Session、同一账号向 `get_friend_list` 发起一次 POST，bkn 从该会话动态计算。严格核验响应成功与完成性后，将各分组的 uin 合并为去重集合，为目标群全部成员赋 `friend / not_friend`，再按群排除→好友排除→已发送过滤处理。未勾选不调用该接口，不改变原成员读取流程。

接口依据是 QQ 网页部署 `7904f18b` 的公开静态脚本：[请求封装](https://cdn-go.cn/qq-qun-web/7904f18b/assets/index.85819934.js) 使用 get_friend_list 表单调用、无额外业务参数并动态带 bkn；[好友选择页](https://cdn-go.cn/qq-qun-web/7904f18b/assets/index.2d8ec08f.js) 在弹窗打开时 await 一次，再用 Object.values(result) 遍历各分组 mems 累加人数，没有分页调用或独立 total。应用据此按当前网页一次性分组响应契约处理；页面人数来自同源数组累计，不能作为独立完整性核验，不能保证腾讯服务端永远返回全量。接口出现显式分页、可选总数不符或异常时拒绝；result 必须为非空分组集合，所有分组均无成员时仅明确 total=0 才接受。这是公开代码行为参考，仍需真实账号联调。

完整好友集合仅存在于本次任务内存，不落库、不跨任务或账号缓存；不增加全好友管理页。仅目标群成员关系、过滤开关与结果随固定快照保存。内部继续保留 `friend / not_friend / unknown`，兼容旧名单和无法确认的关系；旧 `fr` 类型解析仅作历史兼容，不得在新好友读取失败时静默回退。

读取失败、部分结果、必要字段缺失或无法确认完成性时，不保存新名单，原快照保持不变；不能把未读到的成员判为非好友。启用时还检查整个原始目标（含已被群排除者）；残留未知返回 `friend_relation_unknown`。成功后保存开关、实际过滤数、未知数和 `completed` 状态。导出与邮件后台再校验状态、关系、去重和人数守恒，不一致不得继续。目标原始人数核验状态仍独立保留，好友关系明确不能证明群名单完整。

账号（号码和来源）、群、任务版本与过滤规则一起冻结；切换账号、群或重新获取不复用另一份名单的关系。邮件仍绑定原快照，补充数字 QQ 邮箱不能把已过滤好友加回；任意外部邮箱与 QQ 身份没有可靠映射，不推断其好友关系。排除不删除好友、不操作 QQ 客户端。

### 全局手动排除与实时派生

`manual_exclusions` 独立存规范化完整邮箱、可识别的数字QQ号、备注和添加时间；`manual_exclusion_state` 保存独立递增版本。增删与版本同一 IMMEDIATE 事务提交，仅实际变更推进版本；重复项保留原备注，非法输入明确计数。每次添加最多10000非空项/512KiB，备注最多500字符且不含控制字符。批量移除最多10000个ID，任一失效则整批回滚。邮箱域名忽略大小写、本地部分保留，不做别名或跨域身份推断。

原始快照只读，`apply_manual_exclusions` 产生相同ID、获取时间和原始人数的内存副本，新增兼容默认字段 `manualFilteredCount`、`exclusionRevision`。当前页面、缓存群和旧邮件均通过 `get_snapshot_view(snapshotId)` 刷新各自原版本，不换到最近群，也不额外消耗20份保留配额。先还原旧 manual 层再重算，撤销只恢复原快照合格成员；群、好友与已发送层不变。成员选择只收缩，不因撤销自动增选。Excel 保存原因、人数及版本，导出绑定预期版本，过时拒绝。

新增 `get_manual_exclusions`、`add_manual_exclusions({text,note})`、`remove_manual_exclusions({ids})`。写操作与群读取/邮件任务共享 operation 门闩，`ensure_idle` 在等待/停止中也禁止维护，读取不要求QQ登录。提交后清除旧发送计划并广播新revision；若派生刷新失败明确告知已经保存、前端自动补读，不假装事务回滚。诊断只记录操作、数量、版本和安全错误码，不写邮箱或备注。

发送预检统一返回实际名单、sent跳过数、manual排除地址及版本，所有发送入口都使用同一规则；确认令牌绑定排除版本。投递预留的 IMMEDIATE 事务再次检查全部地址，命中排除时先拒绝，不能创建半批sending或unknown记录。没有实际待发地址就不建立任务。成员排除与管理页增删都不创建已发送记录，也不操作QQ客户端。

## 5. 名单核验和失败边界

请求完成与名单完整性是两个状态。核验使用过滤前的目标有效人数，不能用过滤后人数与群总数比较。

| 核验状态 | 含义与后续操作 |
| --- | --- |
| 数量一致 | 独立参考人数与有效去重人数一致，未发现已知截断或刷新冲突。可正常导出，仍以获取时为准。 |
| 名单不完整 | 有少于参考人数、无效号码、明确中断等遗漏证据。可重新获取，或明确导出已取得部分。 |
| 待核验 | 总数缺失、人数冲突、获取期间变化、缓存新鲜度无法确认，或排除群尚未核验。文件和界面保留限制。 |

未知总数保持未知，不能用返回名单长度补出总数再宣称一致。缓存新鲜度缺少证据时保持待核验，不能仅凭请求参数宣称刷新成功。数量一致也可能同时有人进出，因此不承诺同一时刻的不可变全量名单。

排除群部分或待核验时，已知交集仍会移除，但可能还有未知重合成员留在结果中，最终必须标注“排除待核验”。某排除群整个读取失败则停止本次组合任务，不静默跳过。原始目标没有有效记录不能导出伪空结果；原始名单有效、全部被过滤后剩余 0 人则是合法结果。

网络请求有超时，组合获取任务上限为 120 秒；界面不伪造百分比。登录过期、无权限、接口变化、限流和额外验证均显示明确错误，由用户重新登录或等待；不做无期限重试。

## 6. 导出与本机记录

| 格式 | 行为 |
| --- | --- |
| Excel，推荐 | QQ 号、昵称和名片按文本保存；包含最终名单、获取说明及已过滤明细。 |
| CSV | UTF-8 BOM、CRLF，规范处理逗号、引号和换行。危险公式前缀增加单引号；Excel 自动识别长号码的行为仍由 Excel 决定。 |
| TXT | UTF-8 无 BOM、CRLF，最终号码一行一个；合法零结果产生空文件。 |

通过原生保存对话框选择路径，默认文件名包含群号、时间和部分/待核验/已过滤等标记。取消保存不报成功；写入失败不以半成品覆盖原文件。CSV/TXT 不混入已过滤人员，完整明细可在界面和 Excel 查看。

SQLite 位于 Windows 当前用户应用数据目录 `%LOCALAPPDATA%/com.ahui.qq-group-exporter/data.sqlite3`。当前 schema 为版本 5，保留既有模板、资源、手动排除与版本状态表，新增 `account_group_catalog` 和 `latest_group_results`，以 source/account_qq/group_id 复合主键隔离。群目录以 JSON 保存 Group 元信息、顺序及获取时间，成功扫码登录/刷新时同事务替换该账号完整目录；空列表合法，重复或缺失群标识整批拒绝。每群最新结果保存独立 Snapshot JSON，包含成员数字 QQ、昵称、名片、核验状态、过滤前后成员及规则，不建立重复成员行、不保存好友全表或 Cookie。

点击获取成员仍按原流程联网，成功 `save_snapshot` 时同事务写历史、替换该群最新结果并更新群目录元信息；按成功提交顺序更新，不依赖本机时钟单调。群人数优先使用服务端已知 reportedCount，不用筛选后人数冒充。失败/取消不替换原结果；允许保存的不完整或待核验结果保留原状态。全局 snapshots 历史仍保留最近 20 份，每群一份 latest 不受历史淘汰影响；`latest_group_snapshot` 优先每群 latest，`snapshot_by_id` 同时读取历史及仍为每群最新的固定版本，供导出/邮件校验。身份按公开账号核对，缓存不代替登录；刷新目录不删除旧成员结果、不混入其他账号。

好友关系与过滤结果继续随快照 JSON 保存：成员 friendRelation；快照 excludeFriends、friendFilteredCount、friendUnknownCount、friendFilterStatus。旧字段缺失时分别恢复未知、false、0、0、not_requested；历史未知数默认 0 不作关系完整证明，Excel 按实际成员重新统计。启用好友排除需重新获取。已发送记录和公开 SMTP 设置持续保留；密码、授权码、QQ Cookie 不落库。数据库含成员和邮箱等业务数据，并非加密保险箱。

已发送记录是与成员提取、写邮件并列的独立主页面，当前导航统一高亮。支持刷新、搜索、手工粘贴 QQ 号/邮箱、原生选择 UTF-8 TXT/CSV 导入，以及二次确认删除和投递核实。离开页面会取消未提交的确认；从成员或写信进入后可返回原工作区，保留成员选择与邮件草稿。单次历史导入文本上限 4 MiB；界面最多加载最近 10000 条，历史总数及实际过滤使用全库。删除记录会让对应收件人重新成为可发送候选，应在空闲时操作。

投递预留使用 `begin_delivery_with_sender_unless_cancelled(job_id, recipients, sender_address, sender_name, is_cancelled)`；4参 `begin_delivery_with_sender` 保留给无取消检查的旧调用，原2参 `begin_delivery` 继续兼容并传空归属。账号名称/邮箱来自宿主冻结且验证的实际账号配置，跟随 sending、unknown、accepted 持久保存；finish与人工核实成功在同一事务将原delivery快照带入全局sent_history，账号变更不回写。新增 `SentRecord` / `UnresolvedDelivery` 的 `senderAddress`、`senderName` 字段，旧/导入/人工新增默认空，页面兼容缺字段并显示“未记录”，两种搜索覆盖名称与邮箱。按收件人去重的不变量不变，重复成功更新最近归属，非逐封审计流水。

待核实支持逐条复选、本页全选、选择全部、清空和跨页保留选择，刷新剔除已不存在的记录。单条与批量确认共用人数、结论及后果说明，确认后固定 ID；翻页、离开或调整选择撤销未提交确认。`resolve_mail_deliveries({ids, accepted})` 接收 1—10000 个正整数 ID，重复项只处理一次，在单一 SQLite 事务中核对全部仍为待核实后再提交，任一失效或状态变化就整批拒绝，不能前端逐条循环造成部分成功。失败保留选择与确认以便重试，提交使用页面与宿主同步门闩防止重复；成功后替换历史并刷新成员状态。已发送结论添加人工来源，未发送只解除限制，不自动发信。批量核实本身不新增表；当前 schema 为 5。

备份前退出程序，复制整个数据目录，避免遗漏 SQLite 的 WAL 文件；删除数据库会丢失群信息、名单和历史过滤依据。来源字段继续保存原始标识，旧快照未知来源不重写为 web。旧 0/1/2/3/4 库在同一事务升级，v5 在 `sent_history`、`mail_delivery` 各增加 `sender_address`、`sender_name` 两个非空 TEXT 列，默认空字符串；更早库继续创建 v4 两表并按尚存历史回填每群最新，已淘汰数据无法凭空恢复。表、回填与 user_version 一起提交，失败整体回滚，遇高于 5 的版本拒绝打开。升级前退出旧程序并备份整个数据目录；旧程序会拒绝 schema 5，回退需保留新库另存，再恢复升级前完整数据目录备份，不能直接降低 user_version。

## 7. 写信、批量投递与限制

写信使用同一组件的“快捷发送”与“群成员发送”两种收件模式。快捷输入完整邮箱，无需群或QQ会话；两模式独立保留输入地址，共用主题、正文、图片、附件、模板及发件设置，只有当前模式参与预检。由成员页明确交接才切回群模式；普通排除重算不会切换模式。快捷模式不传groupAudience，仍强制全局手动排除、可选历史跳过及待核实阻止。模板只改内容，正式发送仍二次确认；不新增服务或依赖。

写信页围绕已确认的群成员名单布局：来源卡、群收件人明细、可选补充邮箱、主题、附件、基础富文本正文、预览、发件设置和发送进度。群收件地址由所选成员生成 `QQ号@qq.com` 候选，但数字 QQ 号不保证已开通 QQ 邮箱。补充栏只接收完整邮箱，推荐每行一个，也兼容逗号、分号和空白分隔，不再自动把裸 QQ 号改成邮箱。群内和额外地址分开计数、合并去重，无法识别的内容须修正，不静默丢弃。后台旧收件协议与历史导入的 QQ 号解析保留，现有数据库和历史文件无需转换。

前端传递 `snapshotId` 与选中的数字 QQ 号；后台从 SQLite 读取该固定版本，验证选中集合非空且属于最终成员、实际收件地址包含这些候选，不采信前端提供的群名与人数。补充地址不能重新加入该源群中未选中或已过滤的 QQ 号（含好友）；其他补充邮箱明确不属于群资格验证范围。旧快照既不在最近 20 份历史内、也不再是对应群最新结果而不存在时，要求重新确认名单，不能退回无校验发送。

成员表通过只读批量状态查询显示本机全库“已有发送记录／待核实／无发送记录”状态，待核实优先。发送结束与历史维护后刷新状态，避免只靠上次获取的旧名单判断能否重发；它不改变固定名单、导出范围或获取时的过滤人数。邮件任务结果保留后台确定的来源群，可返回成员查看或进入历史核实，成功只表示 SMTP 接受。

支持 SSL/TLS 与 STARTTLS；默认 `smtp.qq.com:465`，可配置其他服务。发件目录最多 20 个，SQLite settings 的 `smtp_sender_accounts_v1` 保存 v1 JSON 目录、revision、稳定账号 ID、名称、公开连接配置和凭据引用，账号目录沿用 settings；当前 schema 为 5。旧 `smtp_public` 首次读取迁为 `legacy-default`，仍引用原 `smtp-credential.bin`；持久空目录标记防止删光后旧账号复活。新授权码按账号 ID 和 SMTP 身份绑定，当前 Windows 用户 DPAPI 加密到固定 `smtp-accounts/` 目录的随机版本文件。先写新密文，再以事务切换目录指针和 revision；SQL 失败不破坏原凭据，提交后清理失败报告真实部分状态并要求刷新。删除/清除不影响共享历史、排除或其他账号；密码/密文不返回页面、不入日志或 SQLite。旧临时密码 IPC 兼容，但当前界面需先保存账号。

正文支持粘贴截图和原生选择 PNG/JPEG/GIF/WebP 图片；按真实内容和头部尺寸校验，拒绝 SVG、远程 URL、本机路径和任意 HTML 图。编辑器使用内存 blob 地址，预览使用登记图片的 data 地址，发送改为受控 CID。普通文字粘贴仍转为纯文本，预览不执行脚本、不加载外部资源。正文图放入 multipart/related，普通附件放在外层 mixed，另保留纯文本 alternative。未另存为模板的图片和附件只驻留内存，关闭即失去草稿；删除图片暂保留撤销缓存，最多 64 张/64 MiB。

### 多 SMTP 账号与固定分配

`mail_accounts` 返回 `{revision,accounts}`，账号公开字段平铺并附 passwordSaved/passwordStatus/passwordMessage；`mail_account_save({input:{id?,name,settings}})`、`mail_account_remove({id})`、`mail_accounts_reorder({ids})`、`mail_account_clear_password({id})` 均返回完整目录。ID/密文版本由宿主生成，重排必须完整且不重复；空选择、缺失账号、重复认证身份、无效格式及超上限拒绝。旧 get/save/clear settings IPC 映射目录首项，未提供多账号字段的旧发送协议继续单账号路径，显式空 accountIds 不能回退。

预检 input 增加 accountIds/accountRevision/sendMode/batchSize/allocationMode，当前页面固定传 random，不提供规则下拉。先从全局历史和排除生成实际唯一名单，再分别用已有 UUID v4 随机键打乱待发地址和所选账号顺序一次，按打乱后顺序均分连续分段。每账号人数为 `floor(N/M)+(index<N%M?1:0)`，人数最多相差 1；人数少于账号数仅随机前 N 账号各 1 人，分到 0 人也在预览明确展示且不解析凭据。随机排序 O(N log N)，最多 10000 收件人；不新增随机数依赖，不保证每次结果不同。旧 IPC 缺省 ordered 保持兼容，显式不支持值拒绝。返回 accountRevision、accountAssignments（accountId/name/fromAddress/recipientCount/messageCount）和 totalMessageCount，固定计划保存随机后的实际地址与账号顺序，并绑定原候选、所选集合、目录 revision、模式与批量；不信客户端账号顺序，提交不再次随机。每个账号单独按 individual=1 或 BCC batchSize 拆批，总封数为各账号封数之和。

start draft 增加 accountIds/accountRevision/allocationMode，当前页面必须携带与预检相同的 allocationMode="random"；省略该字段仅用于 ordered 旧协议兼容，不能与 random 计划混用。提交再核对计划及目录，实际参与账号全部解析并验证 MIME 后才创建任务；不能先发首账号再发现后面凭据无效。目录/授权码、模式/每封人数变化必须重新确认。运行中锁账号管理，任务持有固定 sender/分段名单，队列按轮串行，每轮各账号至多一批；按预检冻结优先序选本轮已经就绪的账号，先跳过冷却者，仅在本轮没有已就绪账号时等待最早截止时间，再重新选择。每账号分配和内部名单顺序保持不变，不因冷却重新随机或转移收件人；各账号上批结果处理完成后刷新独立冷却，取消/终态/新建任务不清空，其他账号耗时计入冷却，无冷却记录的账号仍需满足切换间隔，已耗尽账号不参与本轮等待；失败不自动转移给别的账号、不重新分配，continueOnFailure 只控制后续未尝试批次。所有账号复用同一 Database begin_delivery_with_sender/finish_delivery、全局 sent_history/manual_exclusions/mail_delivery，待核实不能通过换号绕过，仍不把服务端接受宣称为收件箱送达。

默认密送分批，每封 20 人，也可逐人发送；多位收件人通过 BCC 投递，不向彼此展示地址。准备前仅显示候选人数。发送前调用 `prepare_mail_recipients`，后台核对绑定名单和待核实阻止规则，再按“跳过已发送”读取真实全库历史，形成固定收件计划。确认显示计划的实际总数、群成员与补充邮箱人数、已跳过数及预计封数，来源群、各发件账号分配、主题和失败策略同时保留。零收件人不打开发送确认；只有非空附件或正文图片才列出内容数量。

计划令牌只保留在本次草稿内存，5 分钟有效，不进入模板或持久设置。每次发起确认都重新准备；历史或手动排除变更后原令牌整体失效，普通读取刷新不改变版本。前端候选输入、模式、范围、跳过开关、账号目录/选择、每封人数、手动排除版本或任务状态变化也撤销旧确认。`start_mail_job` 携带原候选范围及 `recipientPlanId`，后台核对令牌与历史版本后复用同一份实际名单，不二次过滤、不悄悄改变人数；过期或变更时要求重新确认。准备与提交均锁定草稿和导航，后台独立校验，当前 schema 为 5。

`MailDraft.accountSwitchIntervalSeconds` 省略默认60，显式0—3600有效，非法范围启动前拒绝；前端草稿和确认key包含该值。`SenderCooldownState.last_completion` 只保存上个实际SMTP规范化From身份与单调完成时刻，同进程跨取消/终态/新任务保留；零SMTP本地失败不更新。与目标账号ready_at取max后才参与本轮就绪选择，失败且继续同样计时。此切换记录不持久化，重启恢复的仍是原同账号冷却池。`MailView.waitReason` 可选值 `accountCooldown` / `accountSwitch` / `combined`，无等待时省略，旧调用方可忽略；nextBatchAt表示有效截止，页面统一“等待发送间隔”。

取消在冷却预登记返回后再次检查；投递预留事务在取得IMMEDIATE写锁后及提交前各检查一次。取消返回false时全批回滚，无sending/unknown，不调用SMTP，不更新最近完成身份，仅清冷却pending并保留已登记期限、不续期。闭包只读原子标记，不阻塞或重入数据库；已提交并进入SMTP的当前批仍按原结果处理。这样覆盖SQLite锁等待期间点击停止的边界，不用结果不明记录冒充确定未发送。

账号冷却保存在 `settings.smtp_sender_cooldowns_v1`（version=1），条目为规范化裸 From 身份、recordedAtUnixMs、readyAtUnixMs 和可空 pendingIntervalSeconds；不包含授权码、正文或收件人。SMTP 前 begin 登记 pending，结果记账后 finish 清 pending 并取 max 保留完成后期限，事务失败保留旧记录。无活跃任务时首次 restore 对 pending 按原间隔从恢复时刻保守补足并持久清标记，之后重启只恢复剩余。运行期 AppState 持有按身份映射的单调期限，取消/终态/重建任务不清空，正常等待不写库或续期。仅设置/密码/目录ID变化不改变冷却身份；显式降低新间隔不缩短已生效期限。已登记后本地投递预留失败时保留该次登记但不延长，避免跨模块回滚误删既有期限。

未查实 QQ 对所有账号统一适用的固定 SMTP 每封人数或每日额度，不能把上述数字当作 QQ 官方允许值。真实额度、风控、附件编码后的大小及收件服务器限制可能更低，需要按实际账号规则调整。

只有 SMTP 明确接受后才写入全局已发送记录；这不等于进入收件箱，也不排除后续退信。“失败后继续发送”对应 `continueOnFailure`，默认 false；关闭时遇失败停止后续批次，开启时跳过失败整批，按原轮次与各账号间隔执行后续未尝试批次，不重试、不拆分失败批次。超时、进程中断或结果不明确仍按现有规则保留 unknown／待核实，不能因继续选项而变成已发送或允许自动重发。全部后续批次结束但存在失败时，界面显示“发送结束，部分投递未确认”，不能宣称全部成功。取消等待当前 SMTP 交互结束，再停后续批次。

冷却等待由宿主的单调计时器执行，每轮各账号最多一批，按冻结优先序选择已就绪账号，本轮没有可发账号时才等待最近期限；首轮也核对跨任务留下的冷却。`mail-state` 增加 `phase`（idle/sending/waiting/stopping）、`nextBatchAt`（UTC Unix 毫秒，可空，表示下个批次同时满足两项限制的预计可发送时间，字段名保持兼容）和进程内跨任务单调递增的 `stateRevision`。页面按截止时间计算剩余秒数，不靠渲染次数递减，也不靠页面计时触发投递；较旧版本的同计数事件不能覆盖最新阶段。取消、终态和新批次清除展示截止时间，最后一轮没有等待；current 包含轮次、待发账号与全局尝试批次信息，发送顺序可以因冷却状态变化。新增字段只在内存及事件协议中使用，倒计时本身不新增表；当前 schema 为 5；冷却仍使用 settings，新增 schema 列仅用于发件归属。旧调用省略 `intervalSeconds` 时采用 900 秒，显式 1—3600 秒保持原值。默认间隔不代表服务商允许速率。

`MailView.estimatedCompletionAt` 新增可空 UTC Unix 毫秒字段，只用于当前内存任务和状态事件。开始、等待和批次结果边界，复制 `SenderCooldownState` 后调用与实际调度共用的就绪选择规则模拟剩余冻结队列；执行中的批次只计一次处理时间。每轮至多20个账号，单次模拟 O(剩余批次×账号数)，不写数据库、不联网、不占用状态锁模拟；每批耗时先按10秒，随后用本任务观测均值且至少1秒，等待时间不纳入均值。不在每秒、每个收件人或日志循环中重复计算。双间隔取max、持久同账号池与同进程切换记录都纳入，最后不追加冷却。取消、失败停止及所有终态清空该字段，迟到worker不能写入其他任务。旧调用方可忽略，新页面缺失时不显示；不改变SQLite schema5、冷却格式、账号分配、投递判定和接口入参。页面用本机时区格式化完整日期时间，过期仍运行显示更新中；刷新只读宿主原值，应用重启不恢复任务。回滚只需使用上一EXE或恢复本次源码基线，无数据库迁移或清理要求。


核实前禁止重发，关闭“跳过已发送”也不能绕过。可在本机记录中逐条或批量确认已发送或未发送：前者写入人工核实来源，后者只解除限制，不立即发信。两种操作均须再次确认并明确本次数量，避免重复投递。失败继续和批量核实不改变 SMTP 错误判断规则，没有真实 SMTP 验证结论。

### 邮件内容模板

写信页提供“选择模板”“保存为模板”，管理集中在选择弹窗：搜索名称或主题、预览、新建、编辑、重命名、复制与确认删除。应用后可改当前邮件，只有明确更新模板或另存才持久化，不随正文编辑自动写回。预览/保存/应用不触发 SMTP，正式发送保留二次确认。

内容仅包括名称、主题、基础富文本、正文图片及用户勾选的附件（默认不保存附件）；不包含收件人、来源群、过滤条件、SMTP 身份、授权码或发送参数。应用/编辑/新建覆盖主题、正文、图片和附件整套内容，有原稿时确认并说明附件也替换，取消完整保留。未保存附件的模板应用后附件为空。收件范围和发送设置保持不变。

`mail_templates` 保存元信息，`mail_template_resources` 以 BLOB 保存独立字节副本，外键级联只清理所属模板。更新/复制/删除均在单一 SQLite 事务中提交，无外部文件与数据库半成功窗口，也不引用原文件路径、blob URL 或草稿句柄。应用重新验证图片和数量/大小，生成新句柄与 CID，构造成功后原子交换草稿仓库，失败保留旧资源；删除模板不影响已应用草稿。模板与草稿均不持久化浏览器对象地址。

限制为最多 200 份模板，名称 1—80 字、主题最多 200 字、HTML 2 MiB，允许保存空主题/正文片段；发送仍须符合现有主题/收件规则。资源沿用最多 10 附件+10 正文图、合计 18 MiB、单图 5 MiB 及尺寸校验。模板资源属于本机业务内容，备份需包含 SQLite 数据目录。发送、图片登记或模板操作期间锁定会变更内容的入口，同步门闩防止重复点击和迟到响应覆盖。

模板交换新增 `mail_template_export({ids})`、`mail_template_import_preview()`、`mail_template_import_commit({token,policy})`、`mail_template_import_cancel({token})`。文件路径与资源字节仅在宿主原生对话框/阻塞线程内处理，前端接收轻量名称、主题、资源计数和随机令牌。导出固定 `.qqmailtemplates` 扩展名，同目录临时文件 flush/sync 后原子替换；取消返回 saved=false。导入前后限长 128 MiB，`kind=qq-mail-templates`、`version=1`、UTF-8 无 BOM JSON，各层拒绝未知字段，资源 Base64，正文与解码资源总预算 80 MiB，沿用单模板限制并核对 CID。包包含实际内容和资源，不含本机模板 ID、收件范围、SMTP 设置或登录凭据，无路径展开和外部资源下载。

同名按 trim 后精确区分大小写；copy 默认生成唯一副本，skip 跳过本机或包内先前同名项，overwrite 保留目标 ID/创建时间并整套替换资源。源包重名或本机同名歧义禁止覆盖；前端覆盖冲突项前另行勾选后果确认。预览绑定同一包身份和完整目录基线，5 分钟单调期限；宿主仅保留一包，取消/过期释放，旧计时器不能删除新包。提交在 IMMEDIATE 单事务内复核目录后整批写入，超容量/任一失败整体回滚，目录变更要求重选，可重试数据库失败保留包。成功返回受影响摘要，前端合并列表、按需重读预览，导入不应用草稿、不发送邮件。操作门闩与导航锁防止重复及迟到覆盖。

## 8. 界面样式与使用细节

前端展示职责统一到 `AppToolbar`、`WorkspaceHeader`、`WorkbenchLayout` 和 `DialogLayout`：分别承载全局导航/身份/应用动作、四个工作区标题、配置/结果独立滚动分栏、12类弹窗的标题/滚动主体/固定操作区。它们不读取SQLite、发起IPC、复制业务状态或重建任务。业务组件保留原状态和门禁；`DialogLayout`返回Fragment，确保显式`.dialog-footer`仍为原生dialog直接子节点，通知宿主不能参与底栏定位。

MailComposer保持同一编辑器实例，将附件动作合并到格式栏；低频参数使用原生details按需展开，保留所有默认值/范围/校验。发送栏位于两栏滚动区域之外，占正常文档空间，长正文和配置滚动不改变按钮位置；WorkbenchLayout增加可选sidebarHeader，模式栏放在独立固定区域，下面的aside单独滚动；不使用sticky覆盖正文，原区域名称和tabIndex保留。 展开发送参数以显式mail-option-field和单位span分成标签/112px控件/1em单位三列，无单位的select仍预留末列，所有控件使用36px高度；不再使用margin-left:auto根据尾随单位推位。模式按钮只用aria-pressed表达选中，避免primary主按钮悬停覆盖分段配色。FeedbackHost保留单一Sonner实例及原生dialog portal机制，fixed宿主附在应用根节点或最上层原生dialog末尾，不参与flex/grid分配。悬浮列表按视口顶部居中，宽560px；普通页面top为96px以避开导航，模态内top为16px。最多3条；每条正文高度上限120px并独立滚动，32px关闭键位于卡片内，不随长文滚走。卡片使用垂直居中布局，图标无额外纵向偏移；单行13px文字在56px卡片中的上下留白实测均为18.25px。宿主和列表pointer-events:none，仅可见卡片auto，退出/不可见条目恢复none。显式app-toaster/app-toast选择器避免Sonner运行时后插CSS冲突；堆叠、测量、关闭、去重、暂停、计时和朗读仍由Sonner负责。进入160ms、退出120ms，减少动态效果时归零。移动宿主不重建通知、不重置时限；出现/关闭均不改变页面、正文或操作区坐标。notify只对尚未关闭的同文提示复用ID，onDismiss/onAutoClose立即释放登记；重新出现时创建新ID，防止Sonner旧条目200ms延迟卸载误删新提示，旧回调只释放匹配自身ID的登记。不修改第三方依赖。

成员区重点呈现群摘要、过滤条件、核验说明、结果表和导出；排除群支持搜索、多选与取消选择，已选目标不会出现在候选中。表格内部滚动、工具栏可换行，窗口变窄后上下排布，避免整页横向溢出。空态、群列表失败、搜索无结果和结果合法为零分别提示。

记录页面与写信页共用颜色、字体、间距、边框和交互反馈，支持浅色、深色及窄窗口重排。文本操作采用统一 36px 高、12px 字号与 18px 行高；核实同组按钮同宽，加载和禁用不改变尺寸，纯图标按钮保留独立方形尺寸。Sonner 统一承载登录、保存、导出等操作反馈：成功/普通提示默认 4 秒，错误 7 秒，可手动关闭，同类同文提示去重，最多显示 3 条。提示挂载到当前打开的最上层原生 dialog 内，避免被模态层遮挡；顶部居中的悬浮卡片不占正文空间，主导航与底部操作保持可用，字段校验、任务进度和待核实状态仍留在对应控件。操作加载、失败重试、任务运行禁改、危险操作确认和来源返回都有明确反馈。写信页保持主题、正文、附件和发送摘要顺序清楚；发送期间锁定会改变任务快照的操作，保留取消与进度。错误提示使用可处理的说明，不回显密码、令牌、QQ 完整响应或 SMTP 原始响应正文。

成员区仅保留一次获取统计，正常获取说明折叠、有警告或需核验时展开；零选中隐藏无效的交接/清空动作。群收件人统计与名单入口合并，发送规则按需展开，模板保存操作随上下文显示。排除群、手动排除、发件账号、模板导出合并全选/取消按钮，仍保留搜索外选择；手动标记/导入默认展开，折叠时不卸载输入。发件设置改为左侧账号卡片、右侧分组配置，两区独立滚动，底栏不随表单滚动。全局登录异常、名单不确定、待核实、破坏性确认继续直接可见，不以收起说明替代错误处理。

## 诊断日志

“全选日志”只选择当前显示的只读文本，便于用户自行复制，不自动读取完整文件或申请剪贴板权限。邮箱输入的“全选输入”同样只作用于当前模式的手工文本，不改变群成员范围。

内部 IPC `SessionView` 仅含 `status`（signed_out / active / expired）和公开 `message`；删除 expiresAt、persistenceWarning 及 restore_web_session 命令，宿主和嵌入前端须成套发布。active 只表示本进程最近核验成功，不保证服务端持续接受。没有数据库或配置迁移，SQLite schema 5、SMTP 凭据格式及 purpose 保持不变；回退旧包后也需重新扫码生成旧版会话文件。

手动排除工作区读取期间的新active/revision请求合并为一次补读；离页或卸载使旧响应失效，不能用旧版本解锁维护。读取成功保留输入与仍存在的选择，失败展示重试；宿主持久返回低版本时提示错误而不无限轮询。写入已返回最新完整view时清除多余排队读取，避免一次操作重复刷新。

程序启动自动初始化固定目录 `%LOCALAPPDATA%/com.ahui.qq-group-exporter/logs`；右上角工具栏提供“查看日志”，只读展示当前 app.jsonl 尾部最多 256 KiB 内最近 200 条完整记录，手动刷新与重试，不自动轮询。“打开日志目录”通过宿主打开固定目录查看全部文件和备份，页面不提交路径。读取使用后台阻塞线程，不持有业务任务门闩，不写入、初始化或清理日志；空文件、缺失文件返回空列表，其他 I/O 返回固定错误。日志读取命令不参与前端诊断上报，避免自我记录。UTF-8 无 BOM JSONL 使用 `app.jsonl` 当前文件及 `app.1.jsonl` 至 `app.4.jsonl` 备份，单文件最大 5 MiB，按大小共保留 5 份。备份使用循环槽，编号不代表时间顺序，排查时按文件内 timestamp 或修改时间查看。日志独立于 SQLite，当前 schema 为 5。

宿主记录安全阶段、任务编号、计数、结果和耗时，不记录正文、主题、完整邮箱、密码、授权码、Cookie、二维码或原始响应。前端 `call` 边界只对白名单命令记录 started/succeeded/failed 和毫秒耗时，安全错误码来自固定集合；不传参数、返回值或 error.message。get/poll 成功每个命令 60 秒最多采样一次，失败始终记录。诊断 IPC 直接旁路业务封装，失败吞掉且不递归，不改变原命令结果。

SMTP 日志按 job_id 和 batch_index 关联同一任务与批次，包含服务器、端口、TLS、人数、耗时、错误分类、SMTP 状态码、扩展状态码（如 5.7.1）和脱敏后的服务端错误链；不启用原始协议跟踪，不记录 AUTH、邮件内容或完整地址。成功、失败、跳过、取消及本地结果保存失败分别记录，诊断信息不改变原有待核实与继续发送规则。 SMTP 状态为 550 且服务端明确返回 Too many attempts 时，页面提示“发送过于频繁，请稍后再试”，原因保留在未成功项中；其他 550、认证或网络错误不套用频率提示。详细脱敏响应继续写入日志，不改变原有投递判定。

window error/rejection 只上报固定 kind 与白名单 errorType；error 可附通过严格文件名正则的 JS 包名及正整数行列，不发送完整 URL、查询、DOM、自由消息、堆栈或拒绝原因。`get_log_status` 启动读取并每分钟低频检查，报告命令也返回同一状态；写入故障首次浮层提示并标记日志入口。后续事件最多每 10 秒尝试恢复，日志故障不阻断业务。

发布后需重启新版并重新复现才会产生新诊断；过去未记录的错误无法还原。日志只说明程序执行过程，不能证明真实 SMTP 接受或送达；本次未进行真实 SMTP 验证。日志内容和目录不因模板保存或数据库迁移而混入业务数据。

### 指定成员恢复与错误恢复入口

### 列表显示顺序与分页

`frontend/lib/view.ts` 提供 `compareListLabels` 与 `sortListByLabel`。默认顺序为 ASCII 数字 → ASCII 英文与汉字拼音首字母共用 A–Z → 其他 Unicode 码点。使用固定 `pinyin-pro@3.29.5` 词库逐字转换默认首字母，不做姓名或词义判断；A与阿同级，B与波同级，相同字母继续比较后续键，键相同按持久 ID 稳定排列。未收录汉字保留原码点。数字段比较有效位数和文本，不转浮点数，前导零等价；忽略首尾空白，空字段末尾。全量排序预取每行名称/ID键一次，避免比较时反复拼音转换；不长期缓存用户名称。辅助平面字符整体比较，群头像也取完整码点。

群名/模板名/QQ 号/收件账号分别作为相应列表主字段。目标群和排除群共享同一排序副本；成员、过滤成员、固定群收件人、历史、待核实和手动排除均在完整集合排序后搜索/分页。模板导入预览用固定原包索引区分同名行，不改变宿主包、token 或冲突策略。展示按源集合引用 useMemo 缓存，单次排序 O(n log n) 次比较，额外 O(n) 引用/字段，字符串比较另计字段长度；不会每次输入、勾选或页面计时都重新排序。

所有排序创建新数组，不重排原始快照、导出数据、已冻结的实际分配或输入地址。发件账号保留已有上下移顺序，运行日志/恢复审计保留业务时间顺序。选择和破坏性确认继续绑定稳定 ID，不以行号提交。记录删除或核实使页数缩减时，同步实际页码为有效页，防止数据增长后跳回失效末页。

此前中文排序版本只修改展示层、回归和文档，接口、配置默认值及 SQLite schema 5 不变，无迁移。本轮跳过协议补充见文末。退出新版后使用 `dist/qr-session/QqGroupExporter.exe` 可回滚本次中文拼音排序，不应还原或删除用户数据库。具体命令和验证边界见 `docs/中文拼音排序验收.md`，此前记录保留为历史。

## 本轮交互补充：单次跳过与弹窗操作区

`MailView.waitId` 是当前等待的随机标识（可空），`skip_mail_wait(jobId, waitId)` 仅在当前任务running且waiting、两个标识均匹配时接受。锁内消费一次信号并清除等待标识/截止时间/旧预计完成时间；旧任务、旧等待和重复请求返回 `mail_wait_changed`。内部CancellationToken不序列化、不落盘。等待select优先取消，再跳过，再自然到期；显式跳过只返回当前调度选择的一批，后续照旧查询共享冷却池。真正发送前仍检查取消和阶段门禁，开始/完成照常登记期限。命令不改发送参数、分配、账本及持久冷却，下一批重新计算预计完成时间。前端同步ref防重复，跳过与停止分别锁定，迟到响应沿用stateRevision防回退。

12个有底部操作的弹窗采用统一 `dialog-shell`、`dialog-body`、`dialog-footer` 三段结构；仅中部滚动。不能用last-child匹配操作区，因为通知浮层宿主会动态挂在dialog末尾。页脚不收缩、不覆盖末行，原生dialog关闭时继续隐藏。登录/纯预览弹窗保持既有结构。

新增前端pinyin-pro运行依赖及事件可选字段/命令，无配置默认值或SQLite schema5变更；无需迁移。旧前端可忽略waitId，新前端缺少该字段时隐藏跳过按钮。停止新版后可使用 `dist/pinyin-sort/QqGroupExporter.exe` 回滚，不回退或删除数据库。验证详见 `docs/中英混排与等待及弹窗优化验收.md`。
